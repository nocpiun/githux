## 首版要到达的位置

做出可以实际使用的 **Windows GitHub 桌面客户端**：启动 Home，通过固定侧边栏与基础多标签访问仓库、个人主页和设置；仓库能读取真实分支、文件与 README，在紧凑摘要区展示 Releases、Contributors，并在页面底边展示 Languages；Profile Overview 包含个人 README、Pinned/Popular Repos 和贡献热力图；支持安全登录、多账户保存但单账户活动，以及已缓存内容的离线阅读。

Notifications 与全局 Issues/PRs 的现有功能保留；其余筛选、搜索、New 和新增远程写操作逐项确定最小范围。它们不是被自动排除的功能，也不能由执行者自由扩成完整 GitHub 功能集。

按既有首版边界，Packages、Environments、Profile 的 Repositories/Stars 和 Contribution Activity 延后；其中 Packages 和用户仓库列表已明确进入产品路线图，具体交付批次可单独调整。进阶标签、安装更新和 macOS/Linux 产品适配仍延后。仓库 Issues/PR 列表与详情、PR Conversation 和 Files changed 已接入；其他未设计 Tabs 维持原约定。保留既有四平台 Debug 编译与 artifact，不把编译通过称为跨平台产品支持。

## Windows 日常试用：Issue/PR 阅读清单

负责人只需最新 main，不用切任务分支或建预览 worktree。一次登录后按下面顺序走一遍；无法取得的真实数据单独标为“未覆盖”，不要用合成数据冒充。

### 准备（干净最新 main）

1. 取最新 main 并确认无未提交改动：`git switch main && git pull --ff-only && git status --short`。
2. 用 [README](../README.md#windows-安装与运行) 的正常启动命令 `cargo run --locked` 启动正式应用；首次构建等待编译完成即可，不需要 `cargo build`、测试或预览 example。
3. 在 Settings › Accounts（过渡入口）添加一个真实 Classic PAT 并登录，确认侧栏出现真实仓库列表。

### 1 · 仓库 Issues 列表 → 单条 Issue

1. 侧栏点开一个确有多条 Issue 的仓库，切到页内 **Issues** Tab。
2. 核对列表只含该仓库的 Issue（不混入 PR），Open/Closed 筛选切换，滚动到底出现 **Load more** 并能续页。
3. 点一条标题 → 打开新标签，看到 Issue 正文（Markdown）与普通评论，空正文显示 “No description provided.”，评论可 **Load more comments**。
4. 关掉详情标签，回到仓库页：筛选与滚动位置保持，不重读列表。

### 2 · 仓库 PRs 列表 → Conversation → Files changed

1. 同一仓库切到 **Pull requests** Tab，Open/Closed 筛选，**Load more** 续页，Draft/Open/Merged/Closed 状态可见。
2. 点一条标题 → PR Conversation：摘要（作者、base/head 分支、合并状态）、正文与普通评论；切到 **Files changed** Tab。
3. Files changed 首次点击才读取；文本 diff 有增删与行号，重命名显示原路径，无 patch 显示不可用；**Previous/Next** 分页，空 PR 显示 “No changed files.”。
4. 关掉详情回到仓库页：筛选与分页位置保持。

### 3 · 全局列表与跨入口同一目标

1. 侧栏底部 **Issues** / **PRs** 入口分别打开全局个人列表；核对 Assigned/Created × Open/Closed/All 筛选与 **Load more**。
2. Issue 标题 → Issue 详情，PR 标题 → PR Conversation；同行仓库名链接仍去仓库页，不与标题共用目标。
3. 从 Home 左栏条目标题（或图标、`#number`）打开同一 Issue/PR；Feed 的合并 PR 图标、含 `#number` 的标题与 **Read more** 打开同一 PR。
4. 同账户同一目标从不同入口打开时复用同一标签，不重复建标签；同号不同仓库、同库 Issue/PR 不串。

### 4 · 通知（需真实可识别目标，无则跳过并标注）

1. 账号行右侧铃铛打开 Notifications；只点击 Issue/PR 主题可打开对应详情，其余类型保持纯文本、不猜测跳转。
2. **回退**：若该账户没有相关通知，从全局列表或仓库列表打开同一 Issue/PR 完成跨入口验收，并把“通知直达”标为未覆盖，不要伪造通知。

### 5 · 导航状态与刷新

1. 详情打开后按标签条右侧 Refresh：保留可见内容重读，失败显示 Retry 而不抹掉正文/评论；未登录或授权失效时禁用。
2. 切账户后再打开同一仓库：旧账户标签不复活，旧响应不进入新账户页面。

### 哪些步骤需要真实 Windows / 真实账户数据

- 全部点击、滚动、筛选与视觉观感都需要真实 Windows 窗口与真实 PAT（本清单全部如此）。
- 合成/本地已验证的只是：路由与标签复用、列表筛选/续页/返回保持、Issue/PR 正文与评论渲染、Files changed 懒加载与分页、跨入口目标解析，证据在 `src/app/pages/tests.rs`、`home/shell_nav_tests.rs` 与 `pr_files_integration_tests.rs`；它们不能替代本清单的真实窗口验收。
- 需要真实数据的步骤：登录、通知收件箱（第 4 步）、Feed 关注动态、私有仓库可见性、限流/断网/授权失效提示。若账户没有相关通知或 Feed 事件，按回退执行并标注，不能把“无数据”当作验收通过。


## 仓库与用户主页的后续功能

看完代码、Issue 或 PR 后，用户往往要找“哪个版本包含它”“哪里能拿到发布物”“作者还有哪些仓库”。这三条路径单独排期。下表是建议顺序；之前首版只确认 Releases 摘要、延后 Packages 和 Profile 其他 Tabs 的约定并未因本次规划自动改变。

| 工作项 | 当前基础与建议依赖 | 第一段可验收的体验 |
| --- | --- | --- |
| Releases：版本列表与详情 | [仓库摘要](repository-overview.md)已有 latest/计数；仓库 Releases Tab 仍为空。先复用[发布元数据读取](repository-extras-service.md)，不依赖 Issue/PR 详情。建议在核心阅读主线旁优先推进。 | 从摘要打开对应版本，从 Releases Tab 分页浏览历史；能看 tag、发布日期、Markdown 发布说明和附件名称/大小。能区分最新正式版、预发布与当前账户可见的草稿；只有预发布时仍能浏览。确认无版本时隐藏摘要；请求失败不显示“0 个版本”。附件先提供用户主动打开下载的入口，发布、上传、删除不在这一步。 |
| Profile → Repositories：按用户找仓库 | [Profile Overview](profile-view.md) 只有 Pinned/Popular 摘要；侧栏的仓库范围是登录账户可访问的集合。独立于 Releases，可复用仓库卡片及应用内仓库导航。 | 从本人或他人主页进入 Repositories，分页浏览该用户拥有且当前身份可见的仓库，按名称查找并打开仓库，回来仍在原位置。对他人先保证公开仓库；本人可见的私有仓库须按授权读取。协作仓库不误算成该用户拥有，局部名称筛选不冒充搜完所有分页。 |
| Packages：仓库关联的包与版本 | 当前没有产品页面。先验证包归属、仓库关联与读取权限，再选一种有样例的包类型打通（建议优先容器镜像）；后续再扩展包类型。此项无需等 Releases 做完。 | 从一个有关联包的仓库进入，看到包名、类型和版本；选中版本能查看标识，并复制已核实的安装或拉取命令。用同一 owner 下两个不同仓库验证不串包；查不到关联不能把 owner 的全部包挂到仓库。已确认无包则隐藏摘要，权限不足或数据不全单独处理。不发布、删除或自动执行安装命令。 |

接口核验入口：[GitHub Releases](https://docs.github.com/en/rest/releases/releases)、[用户与仓库列表](https://docs.github.com/en/rest/repos/repos)、[GitHub Packages](https://docs.github.com/en/rest/packages/packages)。开工时用目标账户和代表性样例分别核对，不把产品草案当作 API 能力证明。

除这三项外，后续按使用路径维护候选清单。以下不是已批准的首版菜单：

| 路径 | 可独立交付的一步 | 与已有功能的边界 |
| --- | --- | --- |
| 从代码追历史 | 分支与 Tags 列表 → 提交历史 → 单次提交的文件差异 | 先保留所选 ref 与路径，不把现有分支切换器当历史页；与 PR 的 Files changed 可复用差异展示。 |

## 推进方式

建议先打通一条真实仓库阅读链路，再扩展页面。外壳验证与 API/认证核验可以按依赖分别推进；数据模型从第一次请求就携带账户和资源版本，不留到所有页面完成后返工。

下面的 R1–R6 表示能力顺序，不是必须整批完成才能合并的里程碑。每项可拆成多个小 PR，完成验收后直接合入 main；没有依赖的任务无需等待同一行其他工作。负责人已解除首次试跑的单实现者限制，当前按依赖、文件冲突、编译资源与审查积压安排并行，不固定 Agent 总数。

```mermaid
flowchart TD
    B[已有工程与 CI] --> S[R1 外壳与基础会话]
    B --> A[R2 认证与最小数据通路]
    S --> R[R3 真实仓库阅读]
    A --> R
    R --> H[R4 Home 与 Profile Overview]
    R --> I[R4 顶部信息与设置]
    A --> D[细化 H1-H4 与 H7 的最小范围]
    S --> X[R5 已确定的全局入口与动作]
    A --> X
    D --> X
    R --> W[仓库 Issues/PR 列表与详情]
    W --> T[列表与详情贯通、试用必需项就绪]
    H --> T
    I --> T
    X --> T
    T --> V[Windows 日常试用与 R6 综合验收]
```

R4 各页面可以独立交付；R5 不依赖所有 R4 页面完成。若具体动作涉及某页面或数据类型，只增加那一项依赖。缓存、输入、性能和诊断随各条链路交付，R6 是整体验证，不是第一次处理这些问题。

| 认证与数据 | API 能力核验、凭据、请求执行与取消、存储实验 | 账户上下文、业务模型、缓存键和错误模型 |

| 工程支持 | 派发上下文、审查信号核验、CI 与诊断改进 | 只解决实际交付阻力，不先建设常驻调度平台 |

每个任务一个有效写入者、独立 worktree/PR。共享接口先明确最小数据与错误契约；依赖任务可以先基于 fixture 开发视图，但完成状态必须注明真实数据是否已经接入。不按阶段建立长期集成分支，不为并行而同时修改相同入口。

## 后续任务的进入条件

具体当前优先级与依赖见[下一步依赖](#下一步依赖当前排期不新增产品授权)，这里只保留进入条件，避免旧建议覆盖已交付事实：

- shell-pages 以本基线已合并组件和账户接口为输入，正式路由验证后才标记接通。
- Settings 最终设计与持久缓存应用接线分别需要自己的明确规格；README 图片与各类缓存适配器已合并，未批准的 local-only 方案不自动成为依赖。
- H1–H4/H7、搜索范围和设置首批项目在相关实现前消除范围歧义；基础标签、账户切换恢复、Home/Feed/Profile 默认规则及仓库摘要位置已经确定，不重复裁决。
- 输入/DPI 与综合验收随正式链路推进，不把组件预览或 CI 当最终证据。

近期还需决定是否在试用前读取行内评审线程，以及哪些写操作、搜索与设置项是试用必需的。PAT 权限引导和缓存参数结合所选能力细化；私有内容撤权/移除遵循现有 C1–C5，仍需端到端验证。

## 维护方式

范围变化先更新 [产品约定](product.md)，再调整本路线图的依赖与验收。实现结论更新对应主题及任务开发日志，引用实际 PR/源码；只有验收证据充分时才把任务标为完成。CI 构建成功、页面截图、模拟数据通过和真实产品可用分别记录。

后续候选见[仓库与用户主页的后续功能](#仓库与用户主页的后续功能)：先记录用户路径与依赖，再结合使用反馈确定批次。开发路线图不能替代任务授权，也不能恢复已排除的功能。
