## 首版要到达的位置

做出可以实际使用的 **Windows GitHub 桌面客户端**：启动 Home，通过固定侧边栏与基础多标签访问仓库、个人主页和设置；仓库能读取真实分支、文件与 README，在紧凑摘要区展示 Releases、Contributors，并在页面底边展示 Languages；Profile Overview 包含个人 README、Pinned/Popular Repos 和贡献热力图；支持安全登录、多账户保存但单账户活动，以及已缓存内容的离线阅读。

Notifications 与全局 Issues/PRs 的现有功能保留；其余筛选、搜索、New 和新增远程写操作逐项确定最小范围。它们不是被自动排除的功能，也不能由执行者自由扩成完整 GitHub 功能集。

按既有首版边界，Packages、Environments、Profile 的 Repositories/Stars 和 Contribution Activity 延后；其中 Packages 和用户仓库列表已明确进入产品路线图，具体交付批次可单独调整。进阶标签、安装更新和 macOS/Linux 产品适配仍延后。仓库 Issues/PR Tabs 和单条详情从早期留空阶段进入规划；其他未设计 Tabs 维持原约定。保留既有四平台 Debug 编译与 artifact，不把编译通过称为跨平台产品支持。

### 下一步依赖（当前排期，不新增产品授权）

**当前缺的是仓库范围的列表，以及从各入口打开后的详情。** [全局 Issues/PR](global-work-items.md) 已能按 Assigned/Created、Open/Closed/All 筛选并分页，点仓库名可打开仓库；它回答的是“和我有关的工作”。仓库页应回答“这个仓库有哪些 Issue/PR”，不能套用个人筛选。当前[仓库 Tabs](../src/ui/repository/page_tabs.rs) 仅 Code 有内容；[工作区路由](../src/workspace/mod.rs) 没有单条 Issue，已有单条 PR 在[页面渲染处](../src/ui/page.rs)返回空白。通知的 thread ID 也不是 Issue/PR 编号。

下表是建议的交付顺序。优先级已明确；具体字段、筛选和操作可在对应阶段开工前收敛。不为后续才需要的功能推迟第一条可用路径。

| 顺序 | 用户应该能完成什么 | 建议交付与可观察的完成条件 |
| --- | --- | --- |
| 1 · 仓库 Issues → 单条 Issue | 在某仓库找到一条问题，读懂其内容，再回到刚才的位置 | 第一条纵向任务：复用工作条目行与 Markdown 阅读器。仓库列表先支持 Open/Closed、下一页；详情先显示编号、状态、标题、作者、正文及可分页的普通评论。用同号但不同仓库的两条记录验证路由；列表不混入 PR，关闭详情后保留筛选、已加载页与滚动位置。 |
| 2 · 仓库 PRs → 单条 PR | 知道某个改动做什么、目标是哪条分支、最终是否合并 | 复用第一步的导航、分页、正文和评论；PR 独立表达草稿、打开、未合并关闭和已合并，以及 head/base。先打通 Conversation；建议随后实现 Files changed：文件清单及可读取的文本 diff。二进制、截断或不可用的 diff 要说明原因；是否加入 Commits、Checks、行内评审线程另定。 |
| 3 · 接通已有入口与刷新 | 从仓库、Home 或全局列表打开同一条记录，看到同一份详情 | 同账户内复用同一资源标签，保留现有仓库/用户链接各自的点击行为。Feed 的 Read more 打开 PR 正文；通知仅在能可靠解析类型、仓库和编号时跳转，其余保留原行为。验证首屏有缓存先显示、刷新不闪白、失败可重试，且快速切账户后旧响应不进入新页。 |
| 4 · 定下试用要做的其他事 | 不仅能读，还能明确哪些日常工作要在客户端完成 | 分别定稿全局/仓库 Settings 的首批项目、命令面板搜索范围、收件箱剩余交互以及 New/H7。建议优先讨论发普通评论和创建 Issue，再决定是否需要状态修改、评审提交或合并 PR。每项写明“试用前必需 / 后续 / 不做”；只实现选定项，注明失败反馈及数据更新方式。 |

**可并行的工作：** 第 1 步先约定条目标识（账户上下文、仓库、类型、编号）、打开/复用和返回行为；随后仓库列表与详情读取可分开做，用同一条产品路径验收。PR 特有信息与 diff 可单列任务。Settings 和搜索范围可同时讨论，不阻塞 Issue 阅读；缓存策略沿用[现有约定](cache-strategy.md)，随新页面验证。仓库和全局列表共享呈现，不合并两者的查询语义。

**何时开始 Windows 日常试用：** 在正式应用里能分别从仓库列表打开 Issue 和 PR，读到正文及已约定的讨论/改动信息，从 Home 或全局入口打开同一目标，再回到原列表；能区分确实为空与无权限/加载失败，切换账户不串数据。第 4 步选为试用必需的项目也须可用。各任务仍可先做小范围真窗验证；达到这些条件后再开始整套日常试用。最终 R6 另验真实 PAT、断网/重连与缓存清理、中文 IME、键盘、长列表、多 DPI 和跨屏。

已有 CI 的分支规则是否启用，以仓库实际设置为准。路线图不替负责人修改规则。负责人已于 2026-10-22 解除首次试跑的单实现者限制，并明确按依赖、文件冲突、编译资源与审查积压安排并行；这不改变同一任务同一时刻只有一个有效写入者的要求。

## 仓库与用户主页的后续功能

看完代码、Issue 或 PR 后，用户往往要找“哪个版本包含它”“哪里能拿到发布物”“作者还有哪些仓库”。这三条路径单独排期。下表是建议顺序；之前首版只确认 Releases 摘要、延后 Packages 和 Profile 其他 Tabs 的约定并未因本次规划自动改变。

| 工作项 | 当前基础与建议依赖 | 第一段可验收的体验 |
| --- | --- | --- |
| Releases：版本列表与详情 | [仓库摘要](repository-overview.md)已有 latest/计数；仓库 Releases Tab 仍为空。先复用[发布元数据读取](repository-extras-service.md)，不依赖 Issue/PR 详情。建议在核心阅读主线旁优先推进。 | 从摘要打开对应版本，从 Releases Tab 分页浏览历史；能看 tag、发布日期、Markdown 发布说明和附件名称/大小。能区分最新正式版、预发布与当前账户可见的草稿；只有预发布时仍能浏览。确认无版本时隐藏摘要；请求失败不显示“0 个版本”。附件先提供用户主动打开下载的入口，发布、上传、删除不在这一步。 |
| Profile → Repositories：按用户找仓库 | [Profile Overview](profile-view.md) 只有 Pinned/Popular 摘要；侧栏的仓库范围是登录账户可访问的集合。独立于 Releases，可复用仓库卡片及应用内仓库导航。 | 从本人或他人主页进入 Repositories，分页浏览该用户拥有且当前身份可见的仓库，按名称查找并打开仓库，回来仍在原位置。对他人先保证公开仓库；本人可见的私有仓库须按授权读取。协作仓库不误算成该用户拥有，局部名称筛选不冒充搜完所有分页。 |
| Packages：仓库关联的包与版本 | 当前没有产品页面。先验证包归属、仓库关联与读取权限，再选一种有样例的包类型打通（建议优先容器镜像）；后续再扩展包类型。此项无需等 Releases 做完。 | 从一个有关联包的仓库进入，看到包名、类型和版本；选中版本能查看标识，并复制已核实的安装或拉取命令。用同一 owner 下两个不同仓库验证不串包；查不到关联不能把 owner 的全部包挂到仓库。已确认无包则隐藏摘要，权限不足或数据不全单独处理。不发布、删除或自动执行安装命令。 |

接口核验入口：[GitHub Releases](https://docs.github.com/en/rest/releases/releases)、[用户与仓库列表](https://docs.github.com/en/rest/repos/repos)、[GitHub Packages](https://docs.github.com/en/rest/packages/packages)。开工时用目标账户和代表性样例分别核对，不把产品草案当作 API 能力证明。

除这三项外，后续按使用路径维护候选清单。以下不是已批准的首版菜单：

| 路径 | 可独立交付的一步 | 与已有功能的边界 |
| --- | --- | --- |
| 从代码追历史 | 分支与 Tags 列表 → 提交历史 → 单次提交的文件差异 | 先保留所选 ref 与路径，不把现有分支切换器当历史页；与 PR 的 Files changed 可复用差异展示。 |
| 从仓库找到维护者，再发现项目 | Contributors 完整列表 → Profile；后续是 Stars、Followers/Following | 先贯通已有贡献者摘要、用户主页和仓库入口；个人收藏、关注关系、贡献时间线分别排期。 |
| 从变更看交付结果 | Actions 运行列表与只读结果；Environments / Deployments 的环境和部署记录 | PR Checks、工作流运行、部署记录分别呈现；无权限不报作“没有运行”。重跑、审批与部署另议。 |
| 从提醒找到下一项工作 | 通知直达可识别资源、跨仓库搜索、Settings 和 New 的最小操作 | 复用上方已规划的详情路由。搜索类别和写操作逐项定稿，不引入网页全部菜单。 |

**排期建议：** Issue/PR 的列表到详情仍是下一条主线；Releases 和用户仓库列表可以独立细化，Packages 先完成数据可行性验证。进入 Windows 日常试用前，再据实际使用任务选定是否必须包含这些扩展；不要把整张远期清单都作为试用门槛。

## 推进方式

建议先打通一条真实仓库阅读链路，再扩展页面。外壳验证与 API/认证核验可以按依赖分别推进；数据模型从第一次请求就携带账户和资源版本，不留到所有页面完成后返工。

下面的 R1–R6 表示能力顺序，不是必须整批完成才能合并的里程碑。每项可拆成多个小 PR，完成验收后直接合入 main；没有依赖的任务无需等待同一行其他工作。负责人已解除首次试跑的单实现者限制，当前按依赖、文件冲突、编译资源与审查积压安排并行，不固定 Agent 总数。

```mermaid
flowchart TD
    B[已有工程与 CI] --> S[R1 外壳与基础会话]
    B --> A[R2 认证与最小数据通路]
    S --> R[R3 真实仓库阅读]
    A --> R
    R --> H[R4 Home 与 Profile Overview]
    R --> I[R4 顶部信息与设置]
    A --> D[细化 H1-H4 与 H7 的最小范围]
    S --> X[R5 已确定的全局入口与动作]
    A --> X
    D --> X
    R --> W[仓库 Issues/PR 列表与详情]
    W --> T[列表与详情贯通、试用必需项就绪]
    H --> T
    I --> T
    X --> T
    T --> V[Windows 日常试用与 R6 综合验收]
```

R4 各页面可以独立交付；R5 不依赖所有 R4 页面完成。若具体动作涉及某页面或数据类型，只增加那一项依赖。缓存、输入、性能和诊断随各条链路交付，R6 是整体验证，不是第一次处理这些问题。

## R2：认证与最小数据通路

**目标：** 确认真实数据能按约定安全、可取消地进入 GPUI，建立 R3 必需的最小服务。

- 按已确认的 [PAT 产品登录方案](product.md#登录与未来写能力) 接入 Classic PAT，引导创建、验证身份与权限、系统凭据保存和替换；不建设认证后端。当前先读取，服务边界保留未来写操作的权限判断和写后缓存失效，具体动作另行细化。
- 实现账户元数据、平台凭据引用、活动账户上下文和切换失效机制。多账户保存、单账户活动是基线；不在 UI 或普通数据库保存 token。
- 验证后台执行与 GPUI 的桥接、取消、应用关闭、超时、重试及限流反馈。实际已选 reqwest + Tokio 与 rusqlite 账户目录；具体缓存实现和参数不因这些选型自动确定。
- 建立最小存储版本、可清缓存与用户数据分区、脱敏日志和错误分类。首先只落地仓库链路需要的数据，不一次实现缓存表中所有资源。

**验收：** 应用可识别授权账户并读取最小仓库数据；令牌失效、权限不足、断网和限流不会被显示成有效空列表；切换账户后旧响应不写入新账户的缓存或页面；关闭应用不遗留无归属工作，日志不含凭据。

**当前状态：** 账户目录、系统凭据、真实账户/仓库读取、自动加载和正式 Shell 控制器已由 PR #18/#28/#38 合并；不再描述为“UI 未接入”或“账户元数据未落盘”。每账户 workspace 也已接入。业务内容缓存仍不在这些交付内，真实 PAT 与部分原生交互验收边界见[当前证据表](#当前证据与下一步)。

**已确认：** PAT 为产品登录方式，仓库范围为当前授权下 `/user/repos` 的完整分页可见集合。

## R3：完整的真实仓库阅读链路

**目标：** 登录后能从仓库列表进入仓库，选择分支和文件并阅读内容；中间交付也保持启动 Home 的约定。

- 接入完整可分页的仓库列表、namespace 头像、仓库资料和统计；明确已加载页与完整集合的区别。
- 从分支解析本次浏览的提交版本，使提交说明、文件树和正文对应同一快照；不同标签的浏览选择独立，共享可复用数据。
- 实现 README 默认发现、Markdown 阅读、只读源码查看、选择复制及相对资源解析；验证图片和长内容，不从简单样例推断完整 Markdown 覆盖。
- 覆盖空仓库、没有 README、缺失/不可见文件、非文本或过大内容的边界。具体呈现与读取上限在任务规格中选定。
- 按 [缓存策略](cache-strategy.md) 实现这条链路的结构化快照、固定版本内容和头像磁盘缓存；latest 在确认前不冒充当前最新值。

**验收：** 两个仓库标签可以独立切换分支和文件；快速切换时旧响应不覆盖新页面；关闭一个标签不误取消其他标签共享的读取；重新启动后离线可读之前缓存的仓库内容，但不恢复旧标签集合，仍先进入 Home；无缓存、旧版本与真实空数据可区分。

**当前状态：** 固定快照读取、账户作用域 session、reader 和统一 RepositoryPage 已接入正式 Shell，并由本批 `repository-offline` 接入持久缓存：重启后可按最后已知授权读取已缓存摘要、分支、目录、README、正文与图片，历史快照与当前值分开展示。授权撤权在当前 drain 内清空页面（不依赖定时探测），图片按固定 commit 复用。完整验证边界见[正式页面接入](shell-page-integration.md)与[仓库缓存](repository-cache.md)。

**首个内部自用检查点：** 此链路通过后即可试用仓库阅读，收集真实数据、输入与性能问题；它不代表已完成包含 Home、Profile 等内容的整个首版，也不自动缩减其他保留功能。
